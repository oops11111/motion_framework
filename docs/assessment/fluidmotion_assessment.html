FluidMotion 实施评估：进度、效果与 Windows 界面优化程度

评估日期 2026-10-26 · 依据：仓库 oops11111/motion_framework 的 plan.md、14 张闸门票的结题文件、artifacts/ 中的真机日志，以及本次在 Linux 重新编译、重新运行的单测 · 评估人：Claude（Claude Code 接手会话）

一句话结论：核心前提已经在真机上得到证实，即动效交给合成器后能稳定跑满 60Hz，而 UI 线程只能跑到约 32Hz。但项目在计划第 2 周就进入了 M2 编号，M0 的五项技术验证里，只有指针属性集做过一半（#32 结论 PARTIAL），其余四项都还没做。最近两天的 14 张票里，有 10 张围绕同一个打断续接问题；其中 7 张真机票的结果都是 FAIL 或无定论。成功标准中能在真机上核对的，目前只有很少几项。

总评

工程基础扎实

纯逻辑核心共 3,706 项单测，在 Linux g++ 13 下全部通过；C API 和软件路径演示的 33 项也全绿。

Windows 优化（已测部分）方向成立

合成器路径约 60fps，UI 线程路径约 32fps；弹簧映射误差 ≤0.2%。

打断续接（R-2）未达标

可见跳变从 170 DIP 降到 2 DIP；但速度连续性要求 ≥17/20，最好一次只有 12/20。

成功标准覆盖大部分未测

只有一台 60Hz、Win10、GTX 970 的机器，用 Debug 构建；120Hz、DPI、P95/P99、闲置、Rive 均未测。

二、Windows 界面优化程度

所有数字都来自同一台测试机 DESKTOP-K93N3P8：Windows 10 19045、GTX 970、1280×1024 60Hz 显示器、100% 缩放，MotionSoftDemo 用 WinUI 3 / WASDK 2.5.1 的 x64 Debug 构建。换到别的机器，结论不能直接照搬。

优化程度小结：在“60Hz、单屏、100% 缩放、Debug 构建”这一个点上，下放合成器把动画从约 32fps 提到约 60fps，打断时的可见跳变降低约 99%。速度连续性、高刷新率、性能预算和闲置开销都还没有证据。按 plan.md 的 9 条成功标准算，达成 0 条，部分达成 2 条，未达标 1 条，未测或未开始 6 条。

四、开发建议（按优先级）

回到关键路径：先做 M0

最高

plan.md 的关键路径是 M0 → 分发器 → Rive 宿主 → 指针管线 → 试点。M0 的验收项除指针属性集做了一半外都没做，而 Rive 能不能接进合成表面，决定要不要切换到 Skia 备选方案（切换要多花 4–8 周）。

  • 用 2 周把 Rive 渲染进 CompositionDrawingSurface，同时试一遍 swapchain 路径
  • 测 GetPointerPositionPropertySet、composition swapchain 上的 ALLOW_TEARING，以及实测管线延迟
  • 按 M0 的结果重新估算工期

补第二台机器，而且要选对规格

最高

现在被这件事卡住的有 PERF-CI、R-2 C5(b)、多刷新率矩阵和 frameId 门。建议第二台满足：Win11 22000 以上；120Hz 或 144Hz 显示器；集显或低端笔记本（和现在的 GTX 970 独显错开 GPU 档）；有管理员权限，能走 logman ETL；150% 缩放。一台机器就能同时满足多项闸门要求。

先修 PERF-CI 闸门，再去采数

高

把 PERF-CI 闸门写成判分脚本时发现，有 3 条按现在的写法，首轮必然判不过（详见 docs/m2_perf_ci_tooling_gate_DRAFT.md）：

  • Q1：闲置的应用不会 Present，Idle 场景凑不到 1000 帧。改为按时长统计，或直接断言 0 次 Present
  • Q2：降级路径要求“帧间隔 P95 ≤ T”，垂直同步的抖动使它几乎无法满足。需要加容差
  • Q7：还没有基线。先跑一轮只建基线、不判分

另外，M202Probe.cs 里的 PresentStats 要换成真实统计；正式测量改用 Release 构建。

给打断续接设时间盒，换个思路

高

同一个“seed 取哪里”的方向已经连续 7 张真机票没有通过。建议停止在这个方向上开新的采数票，在下面三种做法里选一种：

  • 产品上接受：发版用 B_v（位置连续），把“改目标时速度可能不连续”写进设计约束和文档。闸门正好禁止把 B_v 当发版基线，所以这一步需要协调显式改裁决
  • 改判据：17/20 smoke 是工程门槛。请设计师在真机上盲测几组打断场景，看可感知的顿挫阈值在哪，再据此决定门槛
  • 换机制：不再从影子轨迹推算 seed。把需要可打断的属性交给合成器自己保存的状态（例如 ExpressionAnimation 读 PropertySet），或用 InteractionTracker 的惯性模型。可行性需要先做一个小原型验证，不确定能否成功

查清 UI 线程只有 32Hz 的原因

高

能力分发器在无法下放时要回到 UI 线程计算。如果 UI 线程本身只有 32Hz，降级后的动画会明显卡顿。31.2 ms 正好是两个 15.625 ms 的时钟节拍，像是计时器分辨率或 WinUI 的 Rendering 节流造成的。这一点 2026-10-20 就记成了“另案处理”，至今没有派单。

让实现回到 plan.md 定下的架构

中
  • C# 现在通过 C ABI 的 P/Invoke 调用引擎。架构要求公开接口走 C++/WinRT 的 WinMD，需要排进 M2 的计划
  • ETW 现在用的是 C# 的 EventSource。计划要求引擎侧用 C++ TraceLogging，否则引擎内部的耗时无法拆分到各阶段
  • Windows 端接上 UISettings.AnimationsEnabled，让 tokens.h 里已经强制提供的 reduced 变体真正生效

给流程减负

中
  • 只有真机采数票保留 DRAFT → LOCK → APPROVED 和哈希锁；纯文档、纯工具的票用一份 PR 加评审就够了
  • 用一份状态表（票、状态、哈希、下一步）取代散在 brief、pack、next 里的追加记录
  • 清理仓库：已提交的 Linux 二进制（code/composition_tests、timeline_tests*）、artifacts/ 中误存的 Windows 路径文件、几百 KB 的原始回复稿，以及 .gitignore 已列出的 bin/、obj/ 之外的构建产物
  • 给 code/ 加 CMake 和 CI（含 ASan/UBSan），这样 Linux 侧的单测证据可以自动复现

证据：plan.md；docs/notion_brief.md §3–4；docs/workbuddy_soft_demo.md；docs/m2_01_result.md、m2_02_result.md 及其余 12 份 *_result.md；docs/side_parked_hang_degrade.md；docs/notion_r2_b_gate_ab.md。单测数字是 2026-10-26 在 Linux g++ 13.3 上重跑的结果（timeline 422 / tokens 743 / controller 236 / composition 2305 / C API 23 / soft-demo 10）。
