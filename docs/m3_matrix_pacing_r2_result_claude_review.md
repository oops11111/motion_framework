## 结论：r2 的改法不对——预算恢复了，但节奏坏了
| 项 | r1（只等垂直同步） | r2（垂直同步后再 DwmFlush） |
|---|---|---|
| 75 Hz 列：每 8 s 帧数 / 间隔 P50 / P95 | 601 / 13.33 / 13.4–13.6 ms | 600–602 / 11.4–12.1 / **16.8–18.6** ms |
| 75 Hz 列偏差 P95（门槛 3.33 ms） | 0.11–0.23 ms ✓ | **5.1–5.3 ms ✗** |
| 180 Hz 列：每 8 s 帧数 / 间隔 P50 | 1442 / 5.556 ms | **907–997 / 7.3–9.8 ms** |
| 180 Hz 列超半周期占比（门槛 5%） | 0% ✓ | **43–60% ✗** |
| 180 Hz 屏 GPU P95 | 1.06·T ✗ | 0.067–0.074·T ✓ |

- **75 Hz 屏**：帧数仍是每秒 75 帧，但 `DwmFlush` 在垂直同步之后的等待长短不一（DWM 按 180 Hz 合成，和 75 Hz 的垂直同步相位一直在变，等 0–5.6 ms），所以每帧开始的时刻抖动，间隔在约 8–19 ms 之间变化。动画按实测间隔推进，帧的时间步长随之抖动。
- **180 Hz 屏**：`DwmFlush` 经常在下一次垂直同步**之后**才返回（它等的是“下一次合成完成”，调用时本次合成可能已开始），于是 `WaitForVBlank` 又多等一个垂直同步，约一半的帧被跳过，只剩约 122 帧/秒。

## 从 r1、r2 两次结果得到的结论
1. **出帧时机必须锚定在窗口所在屏的垂直同步上**（r1 证明这样节奏完美），不能再叠加 `DwmFlush`。
2. **r1 的预算失败来自“往绘制表面拷贝”这一步**：拷贝时 DWM 正在读同一张表面，GPU 要等它读完。等的是 DWM，不是我们的渲染工作（Rive 本身约 0.2 ms）。r1 的 GPU 计时把“Rive 渲染 + 拷贝 + 等待”算在一起，所以无法区分。
3. 这次等待在 180 Hz 屏上的实际影响是：新帧可能晚一次合成上屏（约 +5.6 ms 延迟），帧节奏不受影响（r1：0 超长间隔）。
