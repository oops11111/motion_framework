- **GPU 计时缺陷（探针 bug）**：1.8×10¹⁴ ms 约等于 2⁶⁴ 除以时间戳频率，说明 end 时间戳早于 begin，无符号减法回绕了。原因是 `DrainQueries` 没检查两个时间戳的 `GetData` 返回值，而且 `flags=0` 并不会阻塞等待。AMD 驱动上，disjoint 查询可能先于时间戳就绪，未就绪的时间戳保持 0。NVIDIA（M0-A）恰好没触发。两个会话的 `m0_1b.gpu_p50_ms=0.000` 也是同一原因（两个时间戳都没就绪）。GPU P50 约 0.19 ms 看起来正常，但 P95 无法给出，所以第③条的 GPU 部分不能判定。
- **第④条**：参考图导出修复已生效（M0-A 时为空，这次三张都是 100% 不透明）。参考图与截图的场景、角色、构图完全一致，配色不同：参考图是夜景，截图是白天。原因是参考图取的是动画 t=0.5 s，截图在约 12 s，这个 Rive 文件的天空颜色随时间变化。这不是通道错位：两者亮度差得太远，不可能只是通道互换。判 ✓。
- 首帧 CPU 最大值：s1 为 10.1 ms，s2/s3 约 1.3 ms，远小于 M0-A 的约 440 ms（Win10、NVIDIA）。首帧预热仍然列为 M3 的事项，但这台机器上问题不大。

## M0-4 ALLOW_TEARING（RECORDED）
- CheckFeatureSupport=1；合成交换链和 HWND 交换链带撕裂标志都创建成功，Present 全部 S_OK。
- **新的间接证据**：这台机器上，合成交换链不带标志时，sync 0 被节流到每秒约 169 次 present（被合成节奏阻塞）；带标志时为每秒约 8,963 次，不被阻塞。M0-A（Win10、NVIDIA）两者没有区别。这说明 Win11 上合成交换链带撕裂标志时，present 不再跟着合成器节奏，但仍不能证明屏幕上真的撕裂。没有 PresentMon（未提权），所以拿不到 PresentMode。

## 结论
- 现有数据都支持 Rive 路径可行：Win11/AMD 上表面渲染正常；两层错位约 0.1 ms，远低于门槛；CPU 预算余量很大。
- 但 M0-2 和 M0-1a 都因为**测量侧缺陷**无法按 LOCK 判据判 PASS，所以本票判 **M0-B-INCONCLUSIVE**。M0 不关闭。
